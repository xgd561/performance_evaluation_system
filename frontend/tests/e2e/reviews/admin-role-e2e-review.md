## 一、角色定位

系统管理员（`admin`）是绩效考核系统的**最高权限角色**，负责系统初始化、全局配置、组织管理和数据治理。

---

## 二、主要工作职责（PRD 来源）

| 职责领域 | 具体工作内容 |
|---------|------------|
| **系统配置** | 考核周期配置、岗位 KPI 模板管理、维度权重设置、绩效等级规则、审批链配置 |
| **组织管理** | 员工增删改查、部门管理、岗位管理、员工批量 Excel 导入 |
| **数据治理** | 全公司绩效汇总查看、报表导出（Excel/PDF）、已归档数据解冻修改 |
| **强制分布特批** | 当 HR 的强制分布调整被驳回时，Admin 作为三级特批的最后一级（总经理/系统管理员） |
| **权限与运维** | 角色权限分配、系统冷启动初始化（创建管理员账号）、取消考核、操作日志审计 |

## 四、逐场景深度审核

### 场景 1：登录后仪表盘显示全局统计

#### 业务价值
验证 Admin 登录后能否正确看到**全公司级别**的数据概览，而非个人、团队或部门视角。确保角色隔离在 UI 层生效。

#### 测试脚本实现
```typescript
test('登录后仪表盘显示全局统计', async ({ page }) => {
  await adminLogin(page)

  await expect(page.getByRole('heading', { name: '仪表盘' })).toBeVisible()

  // 通用统计卡片（admin 属于 else 分支）
  await expect(page.locator('.stat-label').filter({ hasText: '员工总数' })).toBeVisible()
  await expect(page.locator('.stat-label').filter({ hasText: '部门数量' })).toBeVisible()
  await expect(page.locator('.stat-label').filter({ hasText: '考核周期' })).toBeVisible()
  await expect(page.locator('.stat-label').filter({ hasText: '进行中' })).toBeVisible()

  // admin 不应显示 manager/employee/peer 的专属快捷操作
  await expect(page.getByText('批量评分')).not.toBeVisible()
  await expect(page.getByText('进入自评')).not.toBeVisible()
  await expect(page.getByText('进入协作评分')).not.toBeVisible()
})
```

#### 测试点拆解与 Bug 发现能力

| 测试点 | 校验方式 | 能发现的 Bug | 发现能力评级 |
|--------|---------|------------|------------|
| 登录成功并跳转仪表盘 | `waitForURL('**/dashboard')` + `toHaveURL` | 登录失败、路由跳转异常、后端 401/500 | ⭐⭐⭐ 高 |
| 页面标题"仪表盘"可见 | `getByRole('heading', { name: '仪表盘' })` | Vue 白屏、组件未渲染、Layout 加载失败 | ⭐⭐⭐ 高 |
| 统计卡片"员工总数"可见 | `locator('.stat-label').filter({ hasText: '...' })` | 后端 `/dashboard` API 异常、数据未返回、统计卡片未渲染 | ⭐⭐⭐ 高 |
| 统计卡片"部门数量"可见 | 同上 | 同上 | ⭐⭐⭐ 高 |
| 统计卡片"考核周期"可见 | 同上 | 同上 | ⭐⭐⭐ 高 |
| 统计卡片"进行中"可见 | 同上 | 同上 | ⭐⭐⭐ 高 |
| **不应显示"批量评分"按钮** | `getByText('批量评分').not.toBeVisible()` | **角色权限混淆**：DashboardView.vue 把 admin 误判为 manager 渲染了经理按钮 | ⭐⭐⭐⭐ **极高** |
| **不应显示"进入自评"按钮** | `getByText('进入自评').not.toBeVisible()` | **同上**：admin 被误判为 employee | ⭐⭐⭐⭐ **极高** |
| **不应显示"进入协作评分"按钮** | `getByText('进入协作评分').not.toBeVisible()` | **同上**：admin 被误判为 peer | ⭐⭐⭐⭐ **极高** |

#### 潜在不足
- ❌ 未断言统计数值的**正确性**（如"员工总数=5"）。E2E 测试原则：不依赖具体数据量，但如能结合已知种子数据做弱断言会更好。
- ❌ 未测试 Admin 的仪表盘是否包含**快捷操作入口**（Admin 本身没有专属快捷操作，这一点已通过 `.not.toBeVisible()` 间接覆盖）。
- ❌ 未测试**点击统计卡片**或**数据下钻**行为（如点击"员工总数"是否跳转到员工列表）。

### 场景 2：可进入员工管理页面

#### 业务价值
验证 Admin 具备员工管理权限，能访问员工列表页。员工管理是 Admin 的核心高频操作之一（增删改、Excel 导入）。

#### 测试脚本实现
```typescript
test('可进入员工管理页面', async ({ page }) => {
  await adminLogin(page)

  await page.goto('/employees')
  await expect(page).toHaveURL(/.*\/employees/)
  await expect(page.locator('table').first().or(page.getByText('暂无'))).toBeVisible()
})
```

#### 测试点拆解与 Bug 发现能力

| 测试点 | 校验方式 | 能发现的 Bug | 发现能力评级 |
|--------|---------|------------|------------|
| 页面 URL 正确 | `toHaveURL(/.*\/employees/)` | 路由守卫错误拦截 Admin 访问员工管理页 | ⭐⭐⭐ 高 |
| 页面存在表格或空状态 | `locator('table').first().or(...)` | 页面白屏、el-table 组件未渲染 | ⭐⭐ 中 |

#### 潜在不足
- ❌ **未测试新增员工**：点击"新增"按钮 → 填写表单 → 提交 → 断言列表刷新。这是 Admin 最高频操作之一，当前完全缺失。
- ❌ **未测试编辑/删除**：如编辑员工部门后是否实时刷新、删除后的二次确认。
- ❌ **未测试 Excel 批量导入**：PRD 明确提到 Admin 可进行员工批量导入（含预览、校验），当前未覆盖。
- ❌ **未测试搜索/筛选**：员工列表的搜索框、部门筛选是否正常。
- ❌ **未测试分页**：当员工数量超过单页限制时，分页组件是否可见。

#### 业务价值

#### 测试脚本实现

#### 测试点拆解与 Bug 发现能力

| 测试点 | 校验方式 | 能发现的 Bug | 发现能力评级 |
|--------|---------|------------|------------|
| 页面 URL 正确 | `toHaveURL` | 路由守卫错误拦截 | ⭐⭐⭐ 高 |

#### 潜在不足
- ❌ **未测试任何表单交互**：这是 Admin 场景的最大短板。系统配置页面包含多个 Tab：

## 六、结论：有 Bug 能通过当前用例发现吗？

### ✅ 能发现的 Bug（当前用例的检测能力）

| Bug 类型 | 具体表现 | 哪个场景能发现 |
|---------|---------|---------------|
| 角色渲染错误 | Admin 仪表盘错误显示了经理/员工/协作人的快捷操作按钮 | 场景 1（`.not.toBeVisible()` 会失败） |
| 路由权限错误 | Admin 被错误拦截，无法访问 `/employees`、`/departments`、`/config` | 场景 2/3/4（`toHaveURL` 会失败） |
| 页面白屏 | Vue 组件未渲染、API 500 导致页面空白 | 场景 1/2/3/4（`toBeVisible()` 会超时失败） |
| 后端 API 异常 | `/dashboard` 统计接口返回错误 | 场景 1（统计卡片不渲染） |

### ❌ 不能发现的 Bug（当前用例的盲区）

| Bug 类型 | 具体表现 | 影响严重程度 |
|---------|---------|------------|
| **系统配置表单交互缺陷** | 修改维度权重后保存失败、Tab 切换错误（P1-15 曾修复的问题） | 🔴 高 |
| **员工管理 CRUD 缺陷** | 新增员工表单提交 500、编辑后数据未刷新、删除无二次确认 | 🔴 高 |
| **Excel 批量导入缺陷** | 格式错误无提示、预览数据错位、导入后部分字段丢失 | 🟡 中 |
| **强制分布特批审批链路** | Admin 作为最终审批人，无法收到特批申请或审批后结果未同步 | 🔴 高 |
| **权限管理缺陷** | Admin 给其他用户分配角色后，被分配用户实际权限未生效 | 🔴 高 |
| **数据归档/解冻** | PRD 提到的"已归档数据解冻修改"功能不可用或状态异常 | 🟡 中 |
| **部门树形操作缺陷** | 树形展开/折叠状态未保持、拖拽排序后数据库未更新 | 🟡 中 |
| **配置生效延迟** | 修改等级规则后，已发起的考核周期未按新规则计算 | 🟡 中 |

## 七、建议补充的 E2E 场景（优先级排序）

| 优先级 | 建议补充场景 | 理由 |
|--------|------------|------|
| **P0** | 系统配置：修改维度权重 → 保存 → 刷新后断言新值回显 | Admin 核心工作，且 P1-15 曾修复 Tab 标签混淆，需回归验证 |
| **P0** | 员工管理：点击新增 → 填写表单 → 提交 → 断言列表新增一行 | Admin 最高频操作，当前完全缺失 |
| **P1** | 系统配置：切换等级规则 Tab → 修改 A/B/C/D 区间 → 保存 | 直接影响绩效计算逻辑 |
| **P1** | 员工管理：Excel 导入流程（上传文件 → 预览 → 确认导入） | PRD 明确要求的功能 |
| **P2** | 部门管理：树形展开/折叠、拖拽排序 | 有 `pytest.skip` 标记的历史债务 |
| **P2** | 强制分布特批：从 HR 申请 → Admin 审批通过 | 需多角色跨页面联动，测试复杂度高 |

---

> **审核人意见**：
> 1. 场景 1（仪表盘）设计良好，`.not.toBeVisible()` 的反向断言是亮点，能有效发现角色混淆。
> 2. 场景 2/3/4 仅验证了"页面能打开"，属于准入性测试，**必须补充操作性测试**（尤其是系统配置表单和员工新增）。
> 3. 建议优先补充 **P0 级场景**（系统配置表单交互 + 员工新增），否则 Admin 的核心工作流在 E2E 中基本处于未覆盖状态。
> 4. 当前 4 个场景无法发现 Admin 工作流中的实质性 Bug（如配置保存失败、员工新增 500），仅能做"页面有没有白屏"的粗粒度检查。
